## A. 简报 v2 勘误与补充（以代码为准）

| # | 简报 v2 | 代码事实 | 结论 |

| 1 | §4.1 看门狗只在连续 4 次自愈失败后才重建 | `AecRef.watch()`（renderer.js 260–312）里 `_heals` **只在重建成功后清零**，写指针恢复时不清。效果是：不是"连续 4 次"，而是"这次启动以来累计 4 次"。每次停滞都 resync 成功，用 2–3 小时也会攒满 4 次，然后照样 `stop()+start()` 重建整条链 | **"开久了"的根因仍在，只是发作间隔从分钟拉长到小时。** 一行修复：写指针恢复时 `_heals = 0` |

## B. 八问

### Q1　看门狗的自愈怎样才不会制造故障？

三条原则：**分级、只动最小单元、有冷却。**

| 级别 | 触发 | 动作 | 影响范围 |
|---|---|---|---|
| L0 观察 | far 写指针 3 秒不动且有远端轨 | 记事件，不动作 | 无 |
| L1 重挂参考 | L0 后仍不动 | `resync()`：只重挂 MediaStreamSource，不碰 worklet、不碰 SAB | 参考链 |
| L2 暂停 AEC | L1 两次后仍不动 | 写 `C_CMD_AEC=0`，AEC 旁路（不拿静音参考自适应），near 照常降噪发送 | AEC |
| L3 重建参考 worklet | L2 持续 10 秒 | 只重建 `aec-ref-worklet`，主降噪链不动；完成后 `C_CMD_RESET` 只复位 AEC 状态，再恢复 L2 | 参考 worklet |

配套规则：
- **计数器在恢复时清零**（修勘误 1）：写指针一动，`_heals = 0`。
- **冷却**：L3 之后 60 秒内不再升级；1 小时内 L3 超过 3 次，停止自愈、在 UI 显示"回声消除已暂停"。
- **自愈本身要记日志**：每次升级写 `event:heal`（级别、原因、耗时），长跑验收看它的频率（04 A1）。
- **永远不重建主降噪链**：主链只在用户换麦、切设备时重建。

### Q2　房间无人发布音频时 far 环该怎样？如何区分正常停滞和参考丢失？

0.4.74 的判据（`anyRemote` 为假就不自愈）方向对，但"有远端轨"不等于"参考链应该在出数据"。用三个可观测量组合判断：

| 远端轨 live | 远端 inbound RTP 在涨 | far 写指针在涨 | 判定 |
|---|---|---|---|
| 否 | — | — | 正常空闲，AEC 旁路 |
| 是 | 否 | 否 | 对端没发（闭麦/断流），正常空闲 |
| 是 | 是 | 是，内容全 0 | 对端静音，正常 |
| 是 | 是 | **否** | **参考丢失**，进入 Q1 的 L1 |

关键是加第二列：`getStats()` 里该 mid 的 `packetsReceived` 在 2 秒内有增长。这一列 0.4.74 没有，所以对端闭麦时也可能误判。

空闲期间 AEC 的正确行为：旁路（不自适应），保留已收敛的滤波器系数；参考恢复后直接用旧系数起步，不从零收敛。

### Q3　饥饿降级：直通 / 补零 / 循环 / 播一次渐隐，按场景怎么选？

| 策略 | 进入 | 持续中 | 退出 | 适用 |
|---|---|---|---|---|
| 循环（0.4.73） | 跳变 | 100 Hz 电音 | 跳变 | 不用 |
| 补零 | 跳变 | 断声 | 跳变 | 不用 |
| 播一次+渐隐（0.4.74） | 跳变（块尾→块头） | 10 ms 渐弱后静音 | **跳变（无淡入）** | 比前两者好，仍有咔哒 |
| **直通 + 2 ms 淡化（0.4.75 草案）** | 无 | 原声，没降噪 | 无 | **所有场景的默认** |

唯一的例外是**自然档以外且开了 AEC、并且对端在外放**：这时直通的原声里有回声。处理办法是饥饿超过 100 ms 才从"直通"切到"淡到静音"，因为 100 ms 以内的回声片段不可闻。这条做成参数 `STARVE_PASS_MAX_MS=100`。

### Q4　48k → 16k 值不值得？音质边界？CPU 收益能否量化？

**值得，只对质量档做，排在第 6 步。**

- **CPU 收益（可量化）：** GTCRN 推理量与采样率线性相关。现测 48k RTF ≈ 0.19（单块 ≈ 1.9 ms/10 ms），16k 理论 ≈ 0.065，加 48k↔16k 重采样约 0.005，合计 ≈ 0.07。低配机（×4–5）从 0.76–0.95 降到 0.28–0.35，**从"贴着实时线"变成"有 3 倍余量"**。验收用 bench 实测，不用这个理论值。
- **音质边界：** 16k 保留 0–8 kHz，覆盖语音基频与共振峰；损失的是 8 kHz 以上的齿音与空气感，以及唱歌、乐器的高频。
- **做法：** 分带——16k 上算增益，插值回 48k 施加到原信号的 0–8 kHz，8 kHz 以上原样直通。这样高频不被降噪但也不丢。
- **服务端降噪：** 在 §1.1 实测数据到之前不下结论。结构上它与"SFU 只转发"相冲突：每路要 Opus 解码 → 推理 → 重新编码，额外约 20–30 ms 延迟，并把 CPU 压到一台可能超卖的 VPS 上。

### Q5　BLOCK 480 → 384（3×128）的收益与风险？

**不改。** 收益：块边界与回调网格对齐，输入延迟少 0–2.7 ms。风险：RNNoise 帧长固定 480，GTCRN 的 STFT hop 也按 480 设计，改 384 要么在 native 内再做 384↔480 重组（多一层缓冲、多 2–8 ms 延迟），要么改模型。两个环形缓冲已经隔开了相位漂移，仿真里它对咔哒贡献为 0。

### Q6　在 SAB 命令通道下切档清历史帧而不爆音？

历史帧 native 已在清（勘误 4）。要做的是让切档"不重建、不跳变"：

1. **renderer**：档位按钮只写 `C_CMD_MODE`，不调 `Mic.start()`；之后显式调用 `_startDenoiseGuard()` 复位守护基线（替代原来依赖重建的副作用）。UI 档位从 native `get_mode()` 读回。
2. **native `set_mode()`**：新引擎 reset 后先空跑一块预热；下一块新旧引擎并行算，做 480 样本等功率交叉淡化；之后释放旧引擎。
3. **延迟对齐**：低延迟档加延迟线到 GTCRN 的 544 样本，切档时时间轴不跳。
4. **代价**：交叉淡化那一块 CPU 翻倍（GTCRN ≈ +2 ms），低配机由 CPU 守护兜底。

### Q7　日志字段与频率，600 KB/天内定位周期性问题？

- **周期行：每 10 秒一行，约 220 字节**，记**本周期增量**（不记累计值）：
  `t, ver, mode, node, ctrl, bypass, sent, underruns, starveEnter, starveMsMax, dropped, govSkips, backlogMax, latMs, procMsAvg, procMsP99, farW, farLag, farResyncs, heals, aecOn, inRtp, outRtp, rttMs, lossPct, jbMs, concealedPct, opusKbps, cpuPct`
  在线 6 小时 = 2,160 行 ≈ 475 KB。
- **事件行（发生才写，每分钟最多 30 条）：** `heal`（级别、原因）、`starve`（时长）、`hard_drop`（块数）、`mode_switch`（从→到、耗时）、`bypass`、`reconnect`、`device_change`、`ice_state`、`app_start`（版本三件套、CPU 型号、核数、内存）。
- **为什么 10 秒：** 0.4.74 前的发作曲线首次在 1.3 分钟、间隔 3–4 分钟，10 秒粒度每次发作有 6 个点以上，足以画出曲线；`starveMsMax` 和 `heal` 事件补足 10 秒内的细节。
- **落盘：** `%APPDATA%/FONG/logs/fong-YYYYMMDD.jsonl`，单文件 1 MB 截断，保留 7 天；"导出诊断"打包最近 3 天。
