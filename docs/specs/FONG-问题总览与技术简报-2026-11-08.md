## 3. 现有音频链路（事实，已核对代码）

### 3.1 客户端拓扑

```
麦克风
  → AudioWorklet（denoise-worklet.js，攒块）
  → SAB 输入环 → Atomics 通知
  → Web Worker（denoise-worker.js，阻塞在 Atomics.wait）
  → Rust native（fong_native.node → dsp crate）推理
  → SAB 输出环 → outWrite++
  → AudioWorklet 每 BLOCK 样本取一块 → 发送轨
```

控制面走 SAB 原子槽（`C_CMD_MODE` / `C_CMD_ENABLE` / `C_CMD_TILT` 等），不走 postMessage。

### 3.2 关键参数

```js
BLOCK      = 480 样本      // 48kHz 下 10ms
OUT_SLOTS  = 12            // 输出环容量 = 120ms
帧率       48kHz 单声道
模型       resources/gtcrn_light48_stream.onnx  789KB（GTCRN 48k）
```

### 3.3 降噪四档

```
0 关闭
1 低占用   RNNoise          CPU ~0.4%
2 质量     GTCRN 48k        CPU ~15%
3 自然     高通 + 自适应噪声门   0ms 延迟，几乎不吃 CPU（默认档）
```

### 3.4 服务端

```
Go 单文件为主（api.go ~2300 行），JSON 落盘 /var/lib/fong/fong.json
withSpace 三态鉴权（accessPublic / accessMember / accessMemberOrBanned）
封禁、频道密码已上线
上传资源在 data/img、data/file（相对 WorkingDirectory，与数据文件不同目录树）
```

## 4. 已定位的缺陷（代码级，附位置）

### 4.1 输出环饱和后不可恢复（**最符合"用一会就坏"**）

```js
// denoise-worklet.js  正常路径：只在消费完一整块时前进，无积压追平
if (this.outCursorBlk >= BLOCK) { this.outCursorBlk = 0; this.outRead++; ... }
if (!forceStarve && this.outRead < outWriteNow) { /* 取数据 */ }
else { /* 饥饿分支 */ }
```

- 输出环一旦被顶到 12 块（120ms），worker 开始丢输入（`dropped++`）
- **旁路路径有追平**（`outRead = outWrite`），**正常路径没有**
- 结果：永久 120ms 滞后 + 周期性丢块

### 4.2 `BLOCK = 480` 与渲染回调 128 不同步

Chromium 音频回调固定 128 样本。480 不是 128 的整数倍，攒块相位每次漂移：

```
128 → 256 → 384 → 512(写入480，余32) → 32 → 160 → 288 → 416 → 544(写480，余64) → …
```

块边界与回调网格永远对不齐，产生周期性时序抖动。

### 4.3 饥饿时输出恒定值（DC 台阶）

```js
outCh[i] = this.last;   // 整块保持同一采样值
```

一块（10ms）维持同一个非零幅度，进出都是阶跃 → 咔哒声；DC 偏移进编码器会额外失真。

### 4.4 `dropped` 有计数但未参与守护判定

`underruns` 触发旁路，`dropped` 只做统计。丢块比饥饿更严重，却不触发任何保护。

### 4.5 无持久化日志（**导致上述问题无法事后定位**）

```
package.json   无 electron-log / winston / log4js
main/preload   无任何写日志文件的代码
%APPDATA%\FONG 只有 Chromium 缓存与 leveldb，无应用日志
```

所有 `console.log('[audio-diag] ...')` 仅在 DevTools 控制台，用户关闭即丢失。

### 4.6 已有但需复核的项

- AEC far-end 参考：已从 `clone(receiver.track)` 改为 `audio.captureStream()`（0.4.73）
- far 环消费：已改为与 near 严格 1:1（0.4.73）
- 双层 AEC 串联：已通过 `echoCancellation: false` 关闭浏览器层（0.4.73）
- 切档：已改为 SAB 运行时切换，不再全量重建（0.4.71/73），但**未清模型历史帧**

## 5. 同类产品的实际做法（已实测挖出，供架构对照）

KOOK 0.112.0 解包结果：

```
传输    声网 Agora（agora_rtc_sdk.dll 32.4MB）
AI 降噪 声网 ai_denoiser_module.wasm 2.8MB + SIMD 变体 2.9MB，端侧 AudioWorklet 内联执行
采样率   16kHz 单声道（input_16000hz_1ch / ns_out_16000hz_1ch / agc_out_16000hz_1ch）
帧长     128 样本
饥饿     直通原始输入（不循环、不补零、不衰减）
切档     AINS Hotrestart（清历史帧），不重建链路
看门狗   处理落后 >2× 预期即 reset，>5% 迟滞即上报事件
参数     Enhan（增强强度）/ NoiseOvEst（噪声过估计）/ extOverDrive / AINS-LowLatency
```

**核心差异：KOOK 在 16kHz 上处理，本项目在 48kHz 上处理——同等音频时长的推理量相差 3 倍。**

声网官方文档同时注明 AI 降噪插件的设备建议为「双核 Intel Core i5+ / RAM 8GB+」，说明端侧 AI 降噪本身有硬件门槛，而非本项目独有。

## 6. 需求约束（必须遵守）

```
1. 只有 5 个真实用户，不能为了性能重构整个媒体层
2. 历史回归频发：0.4.60~0.4.73 期间多次"改一处坏一处"，改动必须可局部回滚
3. 单台 VPS，无额外预算；服务端 CPU 余量有限
4. 不采购商业 RTC（迁移成本 > 收益，且会废弃现有 DSP 成果）
5. 客户端用户多为普通配置机器，无法要求升级硬件
6. 现有 /m/ 手机网页版必须继续可用
```

## 7. 验收判据（建议，供审查者细化）

任何音频相关改动，必须同时满足**负向指标消失**与**正向指标存在**：

```
负向  underruns 增速 ≈ 0（正常通话 10 分钟）
负向  dropped 增速 ≈ 0
负向  backlog（outWrite - outRead）稳定 < 6 块
正向  sent 持续增长（证明链路在跑，不是"指标归零因为没跑"）
正向  node=true / ctrl=true（native 链路已建立）
```

> 该要求来源于本项目的实际教训：曾出现「`underruns` 归零」被判为修复成功，实为链路未建立、计数器根本没有来源。**只消失不存在的指标，不构成通过。**

## 8. 已知的历史教训（写开发文档时应体现）

```
1. 验证付给错的对象（发生 5 次以上）
   - 拿被污染的测试库当产品规模
   - 改完代码没重新构建，测的是旧二进制
   - 拿 0.4.37 的旧审查报告当现状（已落后 31 个版本）
2. 断言写中间量而非用户可感知结果
   - ratio 判据把"降噪有效"判成"链路故障"
   - out=-1（测量失败码）被当作真实电平
   - underruns 阈值测的是采样时机，不是产品退化
3. 静默失败
   - try/catch 吞掉 icacls 错误
   - 降噪切档"UI 显示成功、链路根本没建"
```
