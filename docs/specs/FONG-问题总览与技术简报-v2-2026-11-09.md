## 3. 现有音频链路（已核对代码）

### 3.1 客户端拓扑

```
麦克风
  → AudioWorklet（denoise-worklet.js，攒块）
  → SAB 输入环 → Atomics 通知
  → Web Worker（denoise-worker.js，阻塞在 Atomics.wait）
  → Rust native（fong_native.node → dsp crate）推理
  → SAB 输出环 → outWrite++
  → AudioWorklet 每 BLOCK 样本取一块 → 发送轨

并行：AEC far-end 参考环（aec-ref-worklet.js）
      ← 采集"本机扬声器实际播放的音频"
      ← 0.4.73 起改用 audio.captureStream()（替代 clone(receiver.track)）
      ← 由 sync 定时器（2.5s 守护 + ontrack）做存活校验
```

控制面走 SAB 原子槽（`C_CMD_MODE` / `C_CMD_ENABLE` / `C_CMD_TILT` / `C_CMD_RESET`），不走 postMessage。

### 3.2 关键参数

```js
BLOCK      = 480 样本      // 48kHz 下 10ms
OUT_SLOTS  = 12            // 输出环容量 = 120ms
帧率       48kHz 单声道
模型       resources/gtcrn_light48_stream.onnx  789KB（GTCRN 48k）
```

### 3.3 降噪四档

```
0 关闭
1 低占用   RNNoise          CPU ~0.4%
2 质量     GTCRN 48k        CPU ~15%
3 自然     高通 + 自适应噪声门   0ms 延迟，几乎不吃 CPU（默认档）
```

### 3.4 服务端

```
Go 单文件为主（api.go ~2300 行），JSON 落盘 /var/lib/fong/fong.json
withSpace 三态鉴权（accessPublic / accessMember / accessMemberOrBanned）
封禁、频道密码已上线
上传资源在 data/img、data/file（相对 WorkingDirectory，与数据文件不同目录树）
```

## 4. 0.4.74 已修复的四个根因

### 4.1 far 环看门狗反复重建整条链（主因）

```js
if (this._heals > 1) {
  this.stop();                 // 清空所有参考 + 断开 node
  this.start(ctx, sab);        // 重建整条链
}
```

**发作曲线（6 分钟长跑实测）**

```
1.3m      underruns +14880   jitter 0.1466   ← 爆发
1.8~2.5m  +0                 jitter 0.006    ← 回落
5.3m      +4800
5.8m      +2464
6.1m      +1184
```

**周期性发作，不是持续恶化**——这正是"开久了突然有电流"的形态。

机制：`stop()` 清空参考 → far 环无数据 → AEC 把**静音**当参考 → 恢复时 `takeFar` 看到积压一次跳 160ms → 延迟估计失锁。**看门狗的自愈本身在制造故障。**

### 4.2 `captureStream` 参考被 sync 周期性误删（0.4.73 引入）

```js
// 清理判据：alive.has(id) —— alive 里装的是 track.id
// 但实际存的 key 是 'cap:<mid>' —— 永远不在 alive 里
→ 每次 sync（2.5s 守护 + ontrack）都断开重连 captureStream 参考
```

每 2.5 秒断一次参考，AEC 每隔 2.5 秒失锁一次。

### 4.3 循环播最近一块 → 周期性音调（0.4.73 引入）

0.4.73 把饥饿策略改成"循环保持幅度"，但**饥饿超过 480 样本时同一块重复播放，形成 10ms 周期音调**——本身又是电流声。

已改为：**播一次 + 线性渐隐**（不循环）。

### 4.4 看门狗对"房间无人发布音频"误判

只有自己在说话时，far 环停滞是正常状态。原逻辑无脑自愈，触发 4.1 的重建循环。

## 5. 仍未解决 / 未证实

### 5.1 v1 判断已推翻：输出环饱和不是主因

v1 曾判断「输出环饱和到 120ms 且不可恢复」最符合"用一会就坏"。**0.4.74 的实测否定了这个优先级**：

```
4 分钟长跑  bypass 0%   underruns 全程 0   sent 829 → 24829（精确 100 块/秒）
5 分钟双端  inRTP 881 → 33784   recvRMS 0.17 → 0.15   静音帧 0/6
```

环没有饱和，消费速率精确等于生产速率。真正的主因是 §4.1 的看门狗重建。

**该缺陷仍作为潜在风险保留**（正常路径确实没有积压追平机制，旁路路径有），但降级为"未证实的风险"，不再列为优先项。

### 5.2 仍待验证的项

```
· BLOCK=480 与渲染回调 128 不同步 —— 相位每块漂移，理论上有周期性时序抖动，未测出实际影响
· 饥饿时输出恒定值（DC 台阶）—— 0.4.74 改为"播一次+渐隐"后是否还有咔哒，未单独验证
· dropped 有计数但未参与守护判定 —— 逻辑缺陷仍在
· 切档清模型历史帧 —— 0.4.71/73 已改 SAB 运行时切换，但未清历史帧（KOOK 有 AINS Hotrestart）
· 真实场景 CPU 争抢（如 cs2 抢核）—— 本地 8 个 busy-loop 压不出饥饿，无法复现，必须真机验证
```

### 5.3 无持久化日志（诊断能力缺口，仍未解决）

```
package.json   无 electron-log / winston / log4js
main/preload   无任何写日志文件的代码
%APPDATA%\FONG 只有 Chromium 缓存与 leveldb，无应用日志
```

所有 `console.log('[audio-diag] ...')` 仅在 DevTools 控制台，用户关闭即丢失。
**这是"用一会就坏"类问题反复出现的结构性原因**：每次都要靠现场复现。

```
传输    声网 Agora（agora_rtc_sdk.dll 32.4MB）
AI 降噪 声网 ai_denoiser_module.wasm 2.8MB + SIMD 变体 2.9MB，端侧 AudioWorklet 内联执行

帧长     128 样本
饥饿     直通原始输入（不循环、不补零、不衰减）

看门狗   处理落后 >2× 预期即 reset，>5% 迟滞即上报事件（不是重建整条链）
参数     Enhan（增强强度）/ NoiseOvEst（噪声过估计）/ extOverDrive / AINS-LowLatency
```

**核心差异**

| 项 | KOOK | FONG |
|---|---|---|
| 处理采样率 | 16kHz | 48kHz（同等时长推理量 ×3） |
| 帧长 | 128（= 渲染回调） | 480（≠ 128 整数倍） |
| 饥饿策略 | 直通原声 | 播一块 + 渐隐 |
| 算力不足 | watchdog 上报 + 降级 | 反复重建链路（0.4.74 前） |

声网官方文档同时注明 AI 降噪插件设备建议「双核 i5+ / 8GB+」，说明端侧 AI 降噪有硬件门槛，非本项目独有。

## 8. 验收方法

### 8.1 判据原则

任何音频改动必须同时满足**负向指标消失**与**正向指标存在**：

```
负向  underruns 增速 ≈ 0
负向  dropped 增速 ≈ 0
负向  backlog（outWrite - outRead）稳定 < 6 块
负向  bypass 占比 = 0%
正向  sent 持续增长（证明链路在跑）
正向  node=true / ctrl=true（native 链路已建立）
```

> 来源：本项目曾出现「underruns 归零」被误判为修复成功，实为链路未建立、计数器无来源。
> **只消失不存在的指标，不构成通过。**

### 8.2 测量时长要求（0.4.74 新增）

```
短测（8 秒）      只能证明"启动不崩"，不能证明"开久了没问题"
中测（4 分钟）    能覆盖第一次周期性发作（实测 1.3m 首次爆发）
长测（20-30 分钟）覆盖多轮周期 + 真实 CPU 争抢
```

已验证的两个测试脚本：

```
longrun.mjs             采集 underruns / jitter 的时间曲线
real_audio_quality.mjs  采集对端实际收到的音频（inRTP / recvRMS / 静音帧）
```

**缺一环就不算验收**：只看本地计数器不采对端音频，会漏掉"本地指标正常但对端听不到"的情况。

## 9. 历史教训（写开发文档时应体现）

```
1. 验证付给错的对象（5 次以上）
   - 拿被污染的测试库当产品规模
   - 改完代码没重新构建，测的是旧二进制
   - 拿落后 31 个版本的旧审查报告当现状
2. 断言写中间量而非用户可感知结果
   - ratio 判据把"降噪有效"判成"链路故障"
   - out=-1（测量失败码）被当作真实电平
   - underruns 阈值测的是采样时机，不是产品退化
3. 静默失败
   - try/catch 吞掉错误
   - 降噪切档"UI 显示成功、链路根本没建"
4. 短测当验收（0.4.73 → 0.4.74 的直接教训）
   8 秒测试通过就发布，引入两个新的周期性缺陷
```
